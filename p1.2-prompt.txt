# RepoLens — Build an Embedding-Free, Code-Aware Retrieval System

## 1. Project Context

I am building **RepoLens**, a GenAI-powered application that allows users to ask natural-language questions about GitHub repositories and receive accurate, evidence-based explanations of how the code works.

The application should initially support public GitHub repositories. Users should be able to connect or provide a repository, let RepoLens analyze its source code, and ask questions about its implementation.

Examples of questions users will ask:

- Where does the app prevent unauthorized users from accessing protected routes?
- How does the application refresh expired access tokens?
- Where is payment verification handled?
- How does the frontend communicate with the backend?
- What happens when a user logs out?
- Where are database queries executed?
- How does the application handle errors?
- Which functions are called when a user submits a form?
- How does the application validate user input?
- What happens internally when a user creates a new account?
- Where are environment variables used?
- How does the application process a payment from start to finish?
- Which middleware executes before a particular API endpoint?
- What happens if a database query fails?
- How does a request travel from a frontend component to the backend controller and database?

These questions are primarily about **code behavior, implementation details, relationships between components, and execution flow**, rather than simply finding files containing particular words.

## 3. Primary Architectural Decision: No Embedding Models

I specifically want to build the first version of RepoLens without embedding models.

Do not use:

- Gemini embedding models.
- OpenAI embedding models.
- Hugging Face embedding APIs.
- Locally hosted embedding models.
- Vector databases.
- Vector similarity search.
- Any external service that converts source code or queries into semantic embedding vectors.

The existing Gemini generative model should be used for query interpretation where appropriate, reasoning over retrieved source code, and answer generation.

The system must retrieve relevant code using a combination of:

1. AST-based code indexing.
2. BM25 lexical retrieval.
3. Exact-symbol and identifier search.
4. Code relationship indexing.
5. Query expansion and terminology mapping.
6. Candidate ranking and reranking using non-embedding techniques.
7. Bounded relationship traversal to collect supporting code.

The goal is to build a useful code intelligence system without depending on embedding API quotas or vector infrastructure.

Do not claim that this architecture provides perfect semantic retrieval. Implement it carefully, measure its retrieval quality, and keep the design extensible so embedding-based retrieval could optionally be added in the future.

## 4. Required High-Level Architecture

Implement or adapt the following logical pipeline to the existing codebase.

### Repository ingestion

Fetch or clone the public GitHub repository using the existing integration.

Validate repository identity, default branch, accessible files, and repository metadata.

Respect GitHub API rate limits, repository size constraints, request timeouts, and failures.

### File discovery and filtering

Discover files that are useful for understanding the application.

Exclude irrelevant or generated content, including as appropriate:

- node_modules
- .git
- dist
- build
- coverage
- Generated bundles
- Minified JavaScript
- Binary files
- Lockfiles when they are not useful to the question
- Compiled artifacts
- Generated source files

Use configurable exclusions and allow important excluded paths to be included explicitly.

Do not blindly exclude configuration files, tests, migrations, route definitions, middleware, or package manifests because they are often valuable for repository analysis.

### Parsing and code indexing

Parse supported JavaScript and TypeScript files into structured representations.

### Retrieval

### Context assembly

Construct a limited, evidence-focused context from the most relevant source code.

### Answer generation

Generate an explanation supported by source references.

### Response rendering

Return an understandable answer with file paths, line ranges, code snippets where useful, and explicit uncertainty when evidence is incomplete.

## 5. Code-Aware Chunking and AST Indexing

Do not treat every source file as an arbitrary block of text.

Use AST-based parsing where supported so that the index can identify meaningful code entities.

For JavaScript and TypeScript, evaluate:

- Tree-sitter with appropriate JavaScript and TypeScript grammars.
- The TypeScript compiler API.
- Existing parsing libraries already installed in the project.

Choose a parser strategy that fits the existing architecture. Avoid introducing multiple redundant parsers without a clear reason.

Index entities such as:

- Function declarations.
- Function expressions.
- Arrow functions.
- Class declarations.
- Class methods.
- Constructors.
- Exported functions and classes.
- Imports and exports.
- Variable declarations.
- Call expressions.
- Route definitions.
- Middleware registrations.
- Controller functions.
- Database operations.
- Authentication and authorization checks.
- Error-handling blocks.
- Relevant configuration declarations.
- Tests that exercise important behavior.

For React applications, also index useful component declarations, hooks, event handlers, and API calls.

For Express applications, detect common patterns involving:

- app.get, app.post, app.put, app.patch, and app.delete.
- router.get, router.post, router.put, router.patch, and router.delete.
- app.use and router.use.
- Middleware arrays.
- Authentication and authorization middleware.
- Route handlers and controller references.
- Error-handling middleware.

Do not assume every application follows these conventions. Keep framework-specific extraction modular.

### Chunking rules

Prefer chunks that preserve complete functions, classes, methods, route definitions, and other meaningful units.

For oversized functions or classes, split them into smaller overlapping or logically related segments while retaining their parent entity and source locations.

Preserve the original code exactly where possible. Store normalized text separately for lexical search.

Every indexed entity must have enough metadata to locate its original source.

A record could resemble:

{
  "repositoryId": "repository-id",
  "filePath": "src/middleware/verifyToken.js",
  "entityType": "function",
  "entityName": "verifyToken",
  "startLine": 1,
  "endLine": 15,
  "parentEntity": null,
  "imports": ["jsonwebtoken"],
  "calls": ["jwt.verify", "next"],
  "code": "...",
  "contentHash": "..."
}

This is an illustrative schema, not a requirement to use these exact fields or database structures.

Choose appropriate persistence based on the existing database and application architecture.

Do not store embeddings or create a vector index.

## 6. Build a BM25-Based Lexical Retrieval Engine

Implement full-text retrieval using BM25 or a suitable existing search library.

Evaluate options such as MiniSearch, FlexSearch, or a dedicated search engine, but choose based on the actual project requirements rather than adding a large service unnecessarily.

The retrieval engine must support:

- Natural-language query terms.
- Identifier and function-name matching.
- Case-insensitive search where appropriate.
- Exact matches for code symbols.
- File path and filename matches.
- Relevant framework terminology.
- Search result scoring.
- Deduplication of overlapping chunks.
- Repository-level filtering.
- Configurable candidate limits.
- Deterministic behavior where practical.

Do not rely on substring matching alone.

Do not assume that lexical search automatically understands synonyms or intent.

### Example

Indexed source code:

function verifyToken(req, res, next) {
    const token = req.headers.authorization?.split(" ")[1];

    if (!token) {
        return res.status(401).json({
            message: "Unauthorized"
        });
    }

    try {
        req.user = jwt.verify(
            token,
            process.env.JWT_SECRET
        );
        next();
    } catch {
        return res.status(403).json({
            message: "Invalid token"
        });
    }
}

User question:

"Where does the app prevent unauthorized users from accessing protected routes?"

The query does not necessarily contain the function name verifyToken.

The retrieval system should nevertheless find this implementation through authentication-related terminology, HTTP authorization patterns, token validation, relevant status codes, and route relationships.

Do not hardcode this single example. Build reusable indexing and retrieval logic.

## 7. Query Interpretation and Query Expansion

Implement a query-processing layer that extracts useful search signals from the user's question.

For example:

Question:
"Where does the app prevent unauthorized users from accessing protected routes?"

Possible search signals:

- authentication
- authorization
- protected routes
- route guards
- middleware
- JWT verification
- access tokens
- request rejection
- HTTP 401
- HTTP 403

The system should use these signals to broaden lexical retrieval when exact words are absent from the source code.

Implement query expansion using a combination of:

1. Deterministic terminology dictionaries.
2. Framework-specific conventions.
3. Identifier and symbol extraction.
4. Lightweight query classification.
5. Optional Gemini-based query rewriting.

If Gemini is used to rewrite a query, require structured output that can be validated before use.

Treat generated query expansions as search hints, not as facts about the repository.

The original user query must remain available throughout the pipeline.

Keep the number of expansion terms bounded. Avoid producing hundreds of irrelevant synonyms.

If query interpretation fails, continue using the original query and lexical retrieval.

### Query categories

Initially support these categories:

- Authentication and authorization.
- API request flow.
- Database interactions.
- Frontend-to-backend communication.
- Error handling.
- Input validation.
- Payment processing.
- State management.
- File and module relationships.
- Business logic.
- Configuration and environment variables.
- General code navigation.

Classification must not be a hard requirement for search to work. Unknown questions should fall back to general retrieval.

## 8. Build a Code Relationship Index

This is one of the most important features.

The purpose is to retrieve related implementation details even when they do not share the same keywords.

Build a graph-like relationship index using extracted code metadata.

Potential nodes:

- Files.
- Functions.
- Classes.
- Methods.
- Routes.
- Middleware.
- Controllers.
- Components.
- Database models.
- Tests.
- Configuration modules.

Potential edges:

- IMPORTS.
- EXPORTS.
- CALLS.
- DEFINES.
- REGISTERS_ROUTE.
- USES_MIDDLEWARE.
- HANDLES_REQUEST.
- QUERIES_MODEL.
- RENDERS_COMPONENT.
- INVOKES_API.
- TESTS.
- REFERENCES_SYMBOL.

Use explicit edge names and document what each relationship means.

Persist these relationships using the existing database or an appropriate lightweight representation. Do not introduce a dedicated graph database unless there is a demonstrated need.

### Example relationship chain

For a question about protected routes, the index may discover:

Frontend route
→ API request
→ Express route
→ Authentication middleware
→ Controller
→ Database model

For a question about payments:

Checkout component
→ Payment API call
→ Backend order creation
→ Payment provider integration
→ Payment verification
→ Database update

These chains are examples of possible relationships, not assumptions about every repository.

### Relationship extraction

Use AST information and framework-aware rules wherever possible.

Use static analysis to identify:

- Imports and exports.
- Statically resolvable function calls.
- Route registrations.
- Middleware references.
- Controller references.
- Model usage.
- API endpoints referenced in frontend code.
- Test-to-source relationships.

Do not claim to have built a complete runtime call graph.

JavaScript can use dynamic imports, dependency injection, reflection, computed properties, callbacks, and runtime-generated routes. Mark uncertain or unresolved edges accordingly.

### Relationship traversal

Starting from high-ranking retrieval candidates:

1. Follow useful outgoing and incoming edges.
2. Prioritize relationships relevant to the query category.
3. Limit traversal depth.
4. Limit the number of visited nodes.
5. Avoid cycles and duplicate evidence.
6. Preserve each node's file path and line ranges.
7. Rank related code rather than including every connected entity.

Make traversal depth and result limits configurable.

Do not expand the entire repository graph for every query.

## 9. Candidate Ranking Without Embeddings

Combine lexical scores with structured evidence.

Implement a transparent ranking strategy that considers:

- BM25 score.
- Exact symbol matches.
- Function and class name matches.
- File path matches.
- Route and middleware relevance.
- Relevant imports and calls.
- Query-category relevance.
- Relationship distance from an initial candidate.
- Whether a candidate is a definition, call site, route registration, or test.
- Duplicate or near-duplicate source ranges.

Use normalized or otherwise comparable features before combining scores.

Keep ranking weights configurable and documented.

Avoid assigning arbitrary weights without evaluating their effects.

If optional Gemini-based reranking is added, it must be bounded to a small candidate set and must not be required for basic retrieval.

The system must not require a generative model call merely to perform ordinary lexical search.

Return a ranked set of candidate entities, not just an undifferentiated collection of files.

## 10. Evidence Selection and Context Assembly

The retrieval engine should not send an entire repository to Gemini.

Build a context assembler that chooses the most useful source snippets under a configurable token budget.

It should:

- Prioritize high-ranking candidates.
- Include relevant route registrations and middleware when answering access-control questions.
- Include callers and callees when explaining execution flow.
- Include definitions and call sites when answering where functionality is implemented.
- Preserve important surrounding code.
- Deduplicate overlapping source ranges.
- Keep source references attached to every snippet.
- Respect the Gemini model's current context limits.
- Avoid truncating critical code silently.
- Include tests or configuration only when they materially help answer the question.

Use an appropriate token-counting mechanism if available. Otherwise, use a conservative configurable estimate and handle provider token-limit errors gracefully.

Keep the selected context bounded.

Do not confuse "more code" with "better evidence."

## 11. Gemini Answer Generation

Use the existing Gemini integration.

The model should receive:

- The original user question.
- The repository identity and relevant metadata.
- The selected source snippets.
- The file paths and line ranges for each snippet.
- Relevant relationships extracted by the indexing system.
- Clear instructions for grounding its answer in evidence.

Require answers to:

1. Directly answer the user's question.
2. Explain the implementation in understandable language.
3. Identify relevant files and line ranges.
4. Explain execution flow when sufficient evidence is available.
5. Distinguish directly observed facts from inferred behavior.
6. Acknowledge missing or incomplete evidence.
7. Avoid inventing function names, routes, line numbers, or behavior.
8. Avoid treating comments as proof that the code behaves as documented.
9. Avoid claiming that a route is protected unless the relevant registration and middleware evidence supports that conclusion.
10. Avoid claiming complete repository coverage when indexing was incomplete.

If the evidence is insufficient, the model should explain what was found, what remains uncertain, and which additional files would be useful to inspect.

Do not instruct the model to produce a confident answer regardless of evidence.

### Citation format

Use a consistent citation structure compatible with the existing frontend.

For example:

`src/middleware/verifyToken.js:1-15`

The answer should link to the repository source where possible.

Generate line ranges from actual indexed source locations. Do not let the model invent line numbers.

Validate citations against the evidence supplied to the model. If the model returns invalid or unsupported citations, correct or remove them.

Where practical, return structured answer data containing:

- Answer text.
- Source references.
- Relevant code snippets.
- Evidence summaries.
- Confidence or evidence-quality indicators.
- Any limitations.

Adapt this schema to the existing response format rather than breaking current APIs.

## 12. Incremental Indexing and Repository Updates

Large repositories should not be reprocessed from scratch after every change.

Implement incremental indexing.

For each relevant file, maintain a content hash and sufficient indexing metadata to determine whether it needs reprocessing.

On repository refresh:

1. Discover the current repository files.
2. Compare the current file list and hashes against the previous index.
3. Identify added, modified, deleted, and unchanged files.
4. Parse and index only changed or newly added files.
5. Remove stale entities and relationships for deleted files.
6. Rebuild or update affected relationship edges.
7. Update lexical search documents.
8. Mark indexing status and progress.
9. Record failures and allow retrying failed files.

Ensure changes to exports or function definitions update affected relationships.

Do not leave stale index records after deleting or renaming a file.

Use transactional updates or a recoverable staging-and-promotion strategy where appropriate.

Keep repository indexing idempotent: retrying the same indexing job should not create duplicate entities.

Implement appropriate controls for:

- Concurrent indexing jobs.
- File parsing limits.
- Repository size limits.
- Rate limits.
- Request timeouts.
- Retryable failures.
- Non-retryable failures.
- Cancellation where feasible.
- Progress tracking.
- Partial indexing.
- Recovery after process restarts.

Do not hold a normal HTTP request open while indexing a large repository if the existing architecture supports background jobs.

Expose useful indexing states, such as:

- queued
- fetching
- discovering_files
- parsing
- indexing
- building_relationships
- completed
- partially_completed

Use the project's existing status conventions if they differ.

Track progress with meaningful counters, such as files discovered, files indexed, entities indexed, and failures.

Never mark an incompletely indexed repository as fully indexed.

## 15. Security Requirements

Treat repository source code as untrusted input.

A public repository can contain malicious code, prompt-injection text, misleading comments, or instructions intended to manipulate the model.

The indexing and answer-generation pipeline must not execute repository code.

Do not run npm install, build scripts, test commands, or arbitrary repository scripts automatically as part of indexing.

Treat source code and comments as data, never as instructions that override system prompts or security policies.

Keep tool permissions restricted.

Validate repository URLs and GitHub repository identifiers.

Prevent path traversal and unsafe filesystem operations.

Apply timeouts and resource limits to parsers and file processing.

Use safe temporary directories and clean up temporary repository files when no longer needed.

Keep Gemini credentials server-side.

Validate all model-generated structured output before using it in subsequent processing.

Ensure search results and citations cannot cross repository boundaries.

Avoid logging secrets, complete environment files, or unnecessary source code.

## 18. Retrieval Evaluation

Build a small evaluation dataset of realistic repository questions and their expected supporting source locations.

Measure:

- Recall@K: whether relevant source entities appear in the top K results.
- Precision@K: how many retrieved results are relevant.
- Mean Reciprocal Rank (MRR): how highly the first relevant result ranks.
- Citation validity: whether cited files and line ranges exist.
- Answer faithfulness: whether generated claims are supported by retrieved evidence.
- Latency and Gemini token usage.

Start with a manageable set of manually verified questions, then expand it as the system improves.

Use evaluation results to tune ranking and retrieval rather than adding arbitrary complexity.

Do not claim semantic understanding solely because an LLM generates a plausible response.

## 19. Performance Requirements

Design the system to handle repositories with thousands of relevant source files without requiring all files to be loaded into memory simultaneously.

Use streaming or bounded batches for file processing where appropriate.

Avoid parsing unchanged files repeatedly.

Avoid scanning every file for every question once an index has been built.

Use efficient indexes for entity lookup, symbol lookup, lexical search, and relationship traversal.

Keep query-time work bounded and predictable.

Do not introduce distributed infrastructure prematurely. Start with the simplest architecture that meets measured performance requirements.
